# NextEvent Enterprise Architecture and Implementation Roadmap

Status: planning document only. No implementation has been performed.

## 1. Existing Project Analysis

### 1.1 Solution Structure

The solution currently contains four backend projects and one React client:

```text
NextEvent/
  API/             ASP.NET Core Web API host and composition root
  Application/     CQRS use cases, DTOs, validators, application interfaces
  Domain/          Domain entities
  Persistence/     EF Core DbContext, migrations, seeding, SQL connection factory
  client/          React + TypeScript SPA
```

Project dependency flow:

```text
API -> Application
API -> Persistence
Persistence -> Application
Persistence -> Domain
Application -> Domain
Domain -> no project references
```

The backend follows Clean Architecture with vertical slices inside the `Application` layer. Controllers are thin and dispatch commands/queries through MediatR.

- Clean Architecture
- Vertical Slice Architecture
- CQRS
- MediatR
- EF Core
- ASP.NET Identity
- Thin controllers
- Application command/query handlers
- FluentValidation
- Standard API response envelope

Do not introduce microservices.

Do not introduce a modular monolith restructuring at this stage.


#### Object-Level Authorization (BOLA Prevention)
For endpoints that mutate resources (like `EditEvent` or `DeleteEvent`), authorization cannot rely on request payloads (which can be spoofed) or solely on the controller `[Authorize]` attribute.
- **`IEventAuthorizationService`**: This service acts as a DRY ownership-resolution layer. It loads the entity from the database *first*, extracts its unforgeable `OrganizationId`, and then delegates to `IOrganizationAuthorizationService` to check if the caller has the required permission for *that specific organization*. 

#### Function-Level Authorization (BFLA Prevention)
Access to organizer-specific endpoints is strictly gated at the controller boundary.
- **Controller Boundary Gates**: All mutation endpoints (e.g., in `EventsController`) use `[Authorize(Policy = "ActiveOrganizer")]` instead of a generic `[Authorize]`. This rejects unauthorized roles or inactive profiles before the handler is even invoked, preventing Broken Function Level Authorization.

#### Tenant Isolation Rules

To enforce strict multi-tenant isolation while supporting Platform Admins, the API layer follows these rules:

1. **List Endpoints are Segmented:**
   - Handlers returning lists of data are partitioned by role. For example, `GET /events/my` strictly filters events to only include those belonging to organizations where the caller is an active member or owner. Even if a caller attempts to supply another organization's ID, the query ignores it, preventing cross-tenant data leakage.
   - Platform Admins use entirely separate list endpoints (e.g. `GET /events/admin` or `GET /organizations`) that return unsegmented data across the entire system.

2. **Single-Item Endpoints use Unified Queries:**
   - When fetching a specific resource by ID (e.g. `GET /organizations/{id}`), the query logic remains unified.
   - The query handler enforces access dynamically by checking if the caller meets **any** of the following criteria:
     - Caller has the Platform `Admin` role.
     - Caller is the Organization's Owner.
     - Caller is an `Active` member of the Organization.
   - If the caller fails these checks, a `404 Not Found` is returned instead of `403 Forbidden` to prevent resource enumeration.

### 3.3 Database Convention

Apply these conventions to all new business tables:

- `Id` primary key, UUID/GUID
- `CreatedAtUtc`
- `CreatedByUserId`
- `UpdatedAtUtc`
- `UpdatedByUserId`
- `DeletedAtUtc`
- `DeletedByUserId`
- `IsDeleted`
- `RowVersion` or concurrency token

Use soft delete for business records except immutable ledgers such as payments and audit events.

### 3.4 API Convention

Follow REST conventions:

- Use nouns for routes.
- Keep route casing lowercase.
- Use `GET` for queries.
- Use `POST` for commands that create or perform actions.
- Use `PUT` for full replacement.
- Use `PATCH` for partial state transition.
- Use `DELETE` for soft delete.
- Return `ApiResponse<T>` consistently.

### 3.5 Date and Time Convention

We strictly use `DateTime` (in UTC) across the entire solution, adhering to the following architectural patterns:
- **Audit Timestamps**: Fields like `CreatedAtUtc`, `UpdatedAtUtc`, and `DeletedAtUtc` are pure UTC `DateTime` values mapped to SQL Server's `datetime2(3)`. Millisecond precision (3) is sufficient and saves 2 bytes per row over the default precision (7).
- **Business Event Dates**: Scheduled events require both an absolute point in time (UTC) and a local context (timezone). We store the UTC point in time in a `Date` column (mapped to `datetime2(3)`) and the IANA timezone identifier (e.g. `"Asia/Kolkata"`) in a separate `TimeZoneId` string column. The frontend uses the `TimeZoneId` to format the UTC date into the venue's local time accurately, surviving Daylight Saving Time (DST) changes.
- **UTC Enforcement**: To guarantee JSON serialization outputs the `Z` offset, we configured a global EF Core convention (`UtcDateTimeConverter`) and global Dapper TypeHandlers (`UtcDateTimeHandler`). These automatically intercept all dates from the database and force `DateTimeKind.Utc` before they reach the API.
- **Identity Exemption**: Third-party framework columns (like `AspNetUsers.LockoutEnd`) retain their original `datetimeoffset` types to prevent breaking internal Identity operations.

This split pattern ensures we never lose temporal accuracy while keeping storage costs low and indexing performance high.

## 5. Entity Relationships

Core relationships:

```text
AspNetUsers 1..many Organizations as OwnerUser
AspNetUsers many..many Organizations through OrganizationMembers
OrganizationMembers many..many OrganizationRoles through OrganizationMemberRoles
OrganizationRoles many..many Permissions through OrganizationRolePermissions
Organizations 1..many Events
Categories 1..many Events
Organizations many..many AspNetUsers through OrganizationFollowers
AspNetUsers many..many Events through SavedEvents
Events 1..many TicketTypes
AspNetUsers 1..many Orders
Events 1..many Orders
Organizations 1..many Orders
Orders 1..many OrderItems
Orders 1..many Payments
OrderItems 1..many Tickets
Tickets 0..1 CheckIns
Orders 1..many Refunds
Events 1..many Reviews
Organizations 1..many Coupons
Organizations 1..many Announcements
Organizations 1..many Messages
Messages 1..many MessageReplies
AspNetUsers 1..many Notifications
```

Ownership rules:

- Events must belong to an organization after Phase 2.
- Orders belong to customer, event, and organization.
- Tickets are generated only after successful payment or free checkout.
- Reviews require a completed booking/check-in policy decision.

## 6. Customer Journey

### 6.1 Registration

1. Customer opens register page.
2. Customer submits display name, username, email, password.
3. Backend creates ASP.NET Identity user.
4. Backend assigns `Member` platform role.
5. Backend returns JWT and sets refresh token cookie.
6. Frontend stores access token and redirects customer.

### 6.2 Login

1. Customer submits email and password.
2. Backend validates credentials.
3. Backend rotates refresh token.
4. Backend returns JWT and customer DTO.
5. Frontend stores access token.

### 6.3 Browse and Search

1. Customer visits home page.
2. Customer searches by keyword.
3. Customer filters by category, city, date, price, organization.
4. Backend returns paginated event results.
5. Customer opens event detail.

### 6.4 Booking and Payment

1. Customer selects ticket quantities.
2. Backend validates event status, sales window, capacity, ticket availability, coupon.
3. Backend creates pending order.
4. Customer completes payment.
5. Payment webhook confirms payment.
6. Backend marks order paid.
7. Backend generates tickets.
8. Customer can download tickets.

### 6.5 Review

1. Customer can review after event completion or check-in.
2. Backend ensures one review per event/customer.
3. Review may be published immediately or require moderation.

### 6.6 Follow Organization

1. Customer opens organization profile.
2. Customer follows organization.
3. Backend creates `OrganizationFollowers` row.
4. Customer receives organization announcements/notifications.

### 6.7 Message Organization

1. Customer opens organization profile or order detail.
2. Customer starts message thread.
3. Organization member replies from organizer dashboard.

### 6.8 Notifications

Customers receive notifications for:

- Ticket purchase success
- Event cancellation
- Event updates
- Organization announcements
- Refund status
- Message replies

## 7. Organization Journey

### 7.1 Become Organizer

1. Logged-in customer clicks Become Organizer.
2. Customer enters organization name, slug, description, contact data.
3. Backend creates organization with `pending_verification` or `active` status depending on policy.
4. Backend assigns current user as owner.
5. Backend creates default organization roles.
6. Backend assigns owner role to owner member.
7. Backend may add `Organizer` ASP.NET Identity platform role.
8. User lands on organization dashboard.

### 7.2 Invite Members

1. Owner/Admin invites member by email.
2. Backend creates invitation with token hash.
3. Email is sent.
4. Invitee accepts.
5. Backend creates member and assigns selected roles.

### 7.3 Manage Permissions

1. Owner/Admin opens role management.
2. Backend returns roles and permissions.
3. Owner/Admin changes role permission assignments.
4. Backend protects system role constraints.

### 7.4 Create Events

1. Authorized member creates event draft.
2. Member configures venue, media, ticket types, coupons.
3. Member publishes or submits for platform approval.
4. Backend validates organization status and permissions.

### 7.5 Manage Orders and Attendees

1. Organizer views event orders.
2. Organizer filters paid/refunded/cancelled orders.
3. Organizer exports attendee list.
4. Check-in staff scans ticket QR code.
5. Backend prevents duplicate check-ins.

### 7.6 Analytics

Organizer sees:

- Event views
- Saves
- Ticket sales
- Revenue
- Conversion rate
- Followers
- Review rating

### 7.7 Transfer Ownership

1. Owner selects active member.
2. Backend validates target member.
3. Backend changes `Organizations.OwnerUserId`.
4. Backend ensures new owner has owner role.
5. Backend records audit log.

## 8. Admin Journey

### 8.1 Verify Organizations

1. Admin opens pending organizations.
2. Admin reviews profile and supporting data.
3. Admin approves, rejects, or requests changes.
4. Backend updates organization status and audit log.

### 8.2 Moderate Events

1. Admin reviews pending/reported events.
2. Admin approves, rejects, hides, or removes event.
3. Backend notifies organizer.

### 8.3 Manage Users

1. Admin searches users.
2. Admin views user profile, roles, orders, reports.
3. Admin locks/suspends user if required.

### 8.4 Reports

1. Admin views open reports.
2. Admin resolves or dismisses.
3. Backend stores resolution notes.

### 8.5 Platform Settings

Admin manages:

- Categories
- Commission/tax settings
- Approval policies
- Refund policies
- Feature flags

## 13. Risks

1. Event mutation endpoints are not currently protected by authorization.
2. `AppDBContext` mixes Identity and business tables; acceptable now, but migrations will grow quickly.
3. `IAppDBContext` exposes `DbSet<Event>` directly, which can become broad as entities grow.
4. AI service lives in API layer while registered as application service.
5. Existing `Events` table lacks organization ownership, audit fields, soft delete, status lifecycle, and indexes.
6. Ticket purchasing requires careful consistency around inventory, payment confirmation, and idempotency.
7. Organization RBAC can become complex if not implemented before organizer dashboard features.
8. Frontend currently has no route guards or permission-aware navigation.
9. Current client refresh-token interceptor contains one direct Axios call that must stay consistent with `VITE_API_URL`.

## 14. Recommendations

1. Do not start with organizer dashboard UI. Implement organization foundation and RBAC first.
2. Keep SQL Server as the database provider and standardize all new migrations around SQL Server-compatible types and indexes.
3. Keep the existing Clean Architecture and vertical slice style.
4. Add authorization to existing event mutations before exposing organizer workflows.
5. Add audit fields and soft delete conventions before creating new business tables.
6. Create organizations before ticketing, because orders should belong to organizations for reporting and payouts.
7. Build ticketing with a payment abstraction first, even if the first provider is mocked.
8. Implement organization permissions as application-level checks in handlers or reusable authorization services.
9. Add architecture and integration tests incrementally.
10. Update this roadmap after each completed phase.

## 10. Infrastructure Conventions

### 10.1 EF Core Migrations Assembly

**File:** `API/Extensions/DatabaseServiceExtensions.cs`

The solution is split across two projects that are relevant to EF Core:

| Project | Role |
|---|---|
| `Persistence` | Contains `AppDBContext` and the `Migrations/` folder |
| `API` | Startup / DI composition root, references `Persistence` |

Because the startup project (`API`) differs from the project that owns the migrations (`Persistence`), the following line is explicitly set in `DatabaseServiceExtensions`:

```csharp
sqlOptions.MigrationsAssembly(typeof(AppDBContext).Assembly.GetName().Name);
```

**Why it is needed:**

Without this line, when running EF CLI tools with `API` as the startup project and no `--project` flag, EF Core defaults to looking for migrations in the startup assembly (`API`) rather than `Persistence`. This causes migrations to be created in the wrong project or not found at runtime.

**Benefits:**

- **Correct migration location** — EF Core generates and reads migrations from `Persistence` regardless of which project is the startup project.
- **Simpler CLI commands** — The `--project Persistence` flag becomes optional; `--startup-project API` alone is sufficient.
- **Explicit intent** — Any developer reading the code immediately understands that migrations are owned by `Persistence`, not `API`.
- **Future-proof** — If `AppDBContext` is ever moved to a new assembly, the breaking change is caught immediately at startup rather than silently misbehaving.
- **Zero runtime cost** — The setting is read once at startup; it has no effect on query or transaction performance.

**Effect at runtime vs. tooling:**

| Scenario | Without `MigrationsAssembly` | With `MigrationsAssembly` |
|---|---|---|
| App runtime | ✅ Works (default resolves to `Persistence` correctly) | ✅ Works |
| EF CLI without `--project` flag | ❌ Targets wrong assembly | ✅ Targets `Persistence` |
| EF CLI with `--project` flag | ✅ Works | ✅ Works |

**Conclusion:** Keep `MigrationsAssembly`. It allows simpler CLI commands and makes the intent explicit, at zero runtime cost.

### 10.2 EF Core CLI Commands

Always run EF CLI commands from the solution root or the `API` directory. The `--startup-project` flag is required; the `--project` flag is optional because `MigrationsAssembly` covers it.

**Add a migration:**

```bash
dotnet ef migrations add <MigrationName> --startup-project API --project Persistence
```

**Apply migrations to the database:**

```bash
dotnet ef database update --startup-project API --project Persistence
```

**Remove the last migration:**

```bash
dotnet ef migrations remove --startup-project API --project Persistence
```

> The `--project Persistence` flag is shown for explicitness and is safe to omit only when `MigrationsAssembly` is configured as above.
